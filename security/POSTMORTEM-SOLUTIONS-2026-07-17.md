# Postmortem: Solutions Document Bugs — 2026-07-17

## Баги, которые я допустил (3 критических + 2 архитектурных)

### 🔴 Bug #1: F-153 — вызов transfer() НА EOA вместо токен-контракта

```solidity
// Я написал:
(bool sent, ) = initiator.call(
    abi.encodeWithSelector(IERC20.transfer.selector, initiator, deposit)
);
// Это вызывает transfer() НА initiator (EOA), а НА токен-контракте
```

**Почему пропустил**: Копировал паттерн "low-level call для non-standard tokens" из Treasury, но не проверил **на каком адресе** вызов происходит. Привычка к шаблонному коду без проверки контекста.

**Корневая причина**: Не проверил, что `initiator` — это EOA, а не ERC-20 контракт. Не прочитал строку выше, где `initiator = req.initiator` (adres кошелька пользователя).

**Как предотвратить**: Перед каждым `.call()` проверять: **какой адрес вызывается?** Должен ли он иметь код? Если вызывается `transfer()` — адрес должен быть ERC-20 контрактом, не EOA.

### 🔴 Bug #2: F-149 — пропущена boolean return проверка

```solidity
// Я написал:
(success, ) = token.call(
    abi.encodeWithSelector(IERC20.transfer.selector, recipients[i], amounts[i])
);
// Отбрасываю data — не проверяю boolean return
```

**Почему пропустил**: В комментарии НАПИСАЛ "USDT-style false return" — но в коде этот паттерн НЕ реализовал. Это ирония: я описал проблему в комментарии, но код её игнорирует.

**Корневая причина**: Паттерн USDT false-return (F-004) уже существует в MDAOPaymaster. Я знал о нём, упомянул его в комментарии, но не переиспользовал в новом коде. Это классическая ошибка "комментарий описывает проблему, но код её не решает".

**Как предотвратить**: При использовании low-level `.call()` на ERC-20 ВСЕГДА проверять:
```solidity
(bool callOk, bytes memory data) = token.call(...);
bool success = callOk && (data.length == 0 || abi.decode(data, (bool)));
```
Это не optional — это стандартный паттерн для любого ERC-20 call в проекте.

### 🔴 Bug #3: F-149 rate limit — require внутри цикла

```solidity
// Я написал:
require(
    failedCount * 100 / recipients.length <= 10,
    "Too many failed transfers"
);
// Это ВНУТРИ цикла — revert откатывает ВСЕ успешные переводы
```

**Почему пропустил**: Думал про "anti-spam", но не подумал про семантику revert в Solidity. Require внутри цикла = откат всей транзакции = все 200 получателей не получают ничего. Это ВОЗВРАТ к проблеме F-149.

**Корневая причина**: Не продумал взаимодействие нового кода с существующей логикой. Rate limit — хорошая идея, но размещение внутри цикла превращает его в бомбу.

**Как предотвратить**: При добавлении `require` внутри цикла спрашивать: "Если этот require сработает — что происходит с уже выполненными итерациями?" Если ответ "откатываются" —=require не должен быть внутри цикла.

### 🟠 Bug #4: Emergency Pause — undefined modifier

```solidity
function emergencyPause() external onlyEmergencyGuardian {  // ← объявлен?
    emergencyPaused = true;
    emit EmergencyPaused(msg.sender);
}
```

**Почему пропустил**: Писал код фрагментами, не проверил что modifier `onlyEmergencyGuardian` объявлен в предыдущем блоке. Также не реализовал auto-expiry, хотя написал об этом в обосновании.

**Корневая причина**: Разрыв между описанием (auto-expiry) и реализацией (нет). Код не компилируется.

**Как предотвратить**: При написании solidity-фрагментов: каждый modifier, каждая функция, каждое storage variable — должны быть объявлены. Проверять компилируемость мысленно (или через forge build).

### 🔵 Bug #5: F-142 — преждевременная приоритизация

**Почему пропустил**: Не проверил假设 (assumption) что `key.owner` хранит EOA. Если это SmartAccount — оригинальный check может быть корректен. Нужен интеграционный тест.

**Корневая причина**: Не区分 между "knowing the code" и "knowing the runtime behavior". Статический анализ ≠ dynamic verification.

**Как предотвратить**: Для находок, которые зависят от runtime behavior (что в `msg.sender` при вызове через EntryPoint), требовать интеграционный тест ДО предложения фикса.

## Чек-лист для будущих решений

1. **Каждый `.call()` на ERC-20**: проверяю boolean return? (USDT pattern)
2. **Каждый `.call()`**: вызывается ли на правильном адресе (токен, не EOA)?
3. **Каждый `require` внутри цикла**: откатит ли он уже выполненные итерации?
4. **Каждый modifier**: объявлен ли он? Есть ли storage variables для него?
5. **Каждый `require`**: если сработает — что происходит с state?
6. **Каждый комментарий**: соответствует ли он коду ниже? (не описывает проблему, которую код игнорирует)
7. **Каждый architectural assumption**: проверен ли он тестом? (не статическим анализом)

---

## Системная ошибка

Я писал решения, сосредоточившись на **что** должно произойти (refund deposit, partial execution), но недостаточно проверял **как** (какой адрес вызывается, как обрабатывается return, что делает revert). Это типичная ошибка "architectural thinking without implementation rigor".

**Урок**: Документ решений — это НЕ код. Но если решения содержат код-фрагменты, они должны компилироваться и работать. Half-measures хуже, чем no measures: код, который выглядит правильно, но работает неправильно — худший исход, потому что ревьюер думает что проблема решена.
